# 循环 pattern 与暂停窗口

本方案依据 Metadata 中已有的循环、调用和读写区域信息提取可重复的执行结构；不在 runtime 中硬编码 Cholesky 依赖。本文为新增说明，不替换历史策略文档。

## 执行结构

- 外层解释循环位置，以源码顺序推进当前阶段。
- 中间层识别独立循环和独立嵌套循环，复用其参数变化及独立性关系，生成有界任务窗口。
- 内层保留连续迭代压缩：一个任务保存起点、repeat 和仿射步长，内部连续调用公共算子。
- 不能证明并行的区域按源码顺序执行；窗口返回是暂停位，保证下一窗口读取此前已完成的写入。

第一版采用阶段之间的等待，没有实现跨外层阶段的细粒度 lookahead。这是用户明确允许的暂停位策略，避免为了局部重叠重新引入全图物化。后续以实测决定是否需要减少等待。

## 依赖与存储

独立性由访问区域的仿射几何关系证明。共享只读区域允许并行；不同迭代的写区域与其他迭代的读写区域必须不冲突。证明不成立时保留顺序，不能把拓扑序本身当作独立性的证明。

已证明独立的窗口不生成 CSR 边和逐节点入度；现有持久线程池动态领取压缩任务，完成后同步返回。活动任务随窗口释放，不保留整个运行的历史任务。阶段之间的源码顺序与暂停位表达依赖，不需要逐块查找 writer/readers。

这种表示减少建图和调度存储，不减少必须执行的数值算子次数，也不保证任意源码都能并行。窗口内批次过小、阶段等待和小算子调用本身仍可能限制扩展性。

## 配置与评测

`DAG_SCHEDULE=pattern` 选择循环窗口；`DAG_SCHEDULE=graph` 保留原始全图对照；`auto` 按当前实现选择可用路径。`tools/benchmark.py --schedule` 显式记录所选路径。

统计中 `pattern_windows` 是交付执行的窗口数，`peak_window_tasks` 是最大窗口节点数；pattern 路径的 `graph_bytes` 记录活动窗口的任务容器容量估算，不是全图存量或进程峰值 RSS。`tasks` 仍是压缩展开后的逻辑调用次数。`prepare_seconds` 包含循环绑定、证明、窗口生成与调用前准备，`execute_seconds` 包含窗口执行和等待；选择依据始终是完整 `score_seconds`。

性能评测不预热，使用同输入、相同算子库的冷启动独立进程。先比较窗口路径与旧全图，再比较直接编译的源码循环；后者的原始 demo 计时不含输出分配，单列口径。分别固定分段数比较 worker 数，固定 worker 数比较分段数，避免同时改变两项。公开验收、其他算法功能与数值检查继续使用现有 benchmark。
