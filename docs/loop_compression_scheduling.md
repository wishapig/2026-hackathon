# 单 `For` 循环的压缩与调度策略

本文记录当前实现对“链”的定义和调度粒度选择。这里的链只指同一个 `For` 循环在源码中连续生成的一组任务；它不是任意拓扑路径，也不是把存在依赖的多个算子强行合并。

对应实现提交为 `6c900fc`；本文补充 [运行时设计](runtime_strategy.md) 和 [实现说明](implementation.md) 中的历史描述。需求来源仍为 [REQUIREMENTS.md](../REQUIREMENTS.md) 和用户后续明确要求，本文不新增环境限制。

## 压缩对象

当前实现只压缩满足以下条件的循环：

1. 循环体直接包含一个 `Call`。
2. 调用参数和读写区域关于循环变量是仿射变化。
3. 区域形状保持不变，offset 固定或按 `rows * stride` 沿连续行方向移动。
4. 不存在跨迭代的读写冲突。

无法证明这些条件时，Metadata 仍按原始逐迭代任务展开，因此压缩不会改变不适用源码的语义。

一个压缩任务保存第一项的参数、每个参数和访问区域的迭代步长，以及 `repeat`。运行时在这个任务内部按步长逐项调用官方 `cholesky`、`trsm` 或 `madd` ABI。压缩减少任务对象、依赖边、就绪通知和队列操作，保留算子调用次数、参数、访问范围和必须保持的冲突顺序。段内按迭代顺序执行，独立段之间允许并行和重排。

## 两种分块参数

`DAG_LOOP_CHUNK` 是固定上限：每个压缩任务最多包含指定次数的循环迭代。

`DAG_LOOP_PARTS` 是均分策略：一个循环的迭代区间被切成指定数量的连续段，段长度最多相差 1。例如 100 次迭代和 `DAG_LOOP_PARTS=20` 会生成 20 段，每段 5 次；103 次迭代会生成 20 段，其中 3 段包含 6 次、其余包含 5 次。`DAG_LOOP_PARTS` 为正时优先于 `DAG_LOOP_CHUNK`；设置 `DAG_LOOP_CHUNK=1` 且 `DAG_LOOP_PARTS=0` 可保留原始逐迭代任务。

如果循环迭代次数不超过目标段数，当前实现不做压缩，因为此时每段最多只有一项，压缩不能减少任务数。循环不是直接单 `Call`、表达式不是仿射形式、区域不满足连续移动条件或独立性证明失败时，也会回退到原始路径。

`DAG_MAX_STEPS` 为正时维持原解释路径。scalar 应用关闭此压缩；blocked 的自动压缩在串行流式路径中使用 `parts=1`，避免生成无用的并行分段。

## 为什么默认约除以 2

blocked 模式没有显式设置 `DAG_LOOP_CHUNK` 或 `DAG_LOOP_PARTS` 时，使用：

```text
parts = max(1, (planned_workers + 1) / 2)
```

因此目标环境中实际选择为：

| planned workers | 默认 parts |
|---:|---:|
| 16 | 8 |
| 20 | 10 |
| 24 | 12 |

这个“除以 2”是任务粒度启发式，不是把计算限制在一半核心，也不是覆盖评测环境的固定线程上限。实际 worker 数仍由 runtime 的资源策略和 `DAG_THREADS` 决定；`parts` 只控制每个独立循环被切成多少个可调度段。

选择约 `workers/2` 的原因是同时控制两类开销：

- `parts` 接近 workers 时，一个循环能给每个 worker 提供一个段，但每段较短。任务对象、依赖边、原子递减、队列入队和窃取次数会继续增加，建图时间和调度时间可能吞掉细粒度带来的并行度。
- `parts` 远小于 workers 时，图很小，但一个段包含太多迭代。段本身不可抢占，关键路径变长；当某个外层循环只产生少量段时，部分 worker 没有可执行或可窃取工作。
- 取约一半时，每个段大约承载“每核一段”两倍的迭代工作。单个循环仍然提供多个可并行段，而多个外层循环可以同时提供更多段；与此同时，物理任务数和依赖通知数会显著少于完全展开图。

这不是对所有 DAG 的数学最优值。它只利用当前源码可证明的独立迭代结构，并以准备开销、关键路径和可用并行任务数的折中作为默认值。显式 `DAG_LOOP_PARTS` 可以覆盖该启发式，目标机上应以完整 `score_seconds` 复测后决定是否覆盖。

例如 24 个 workers、一个包含 120 次迭代的循环：分 24 段时每段 5 次；默认分 12 段时每段 10 次。如果当前只有这个循环就绪，最多只有 12 个 workers 执行它，其余 workers 可能空闲。只有其他循环也有就绪任务时，才可能继续用满 24 个 workers。因此除以二确实可能牺牲局部并行度，并不保证总用时一定更短。均分的是迭代数，段由就绪队列动态领取，没有固定绑定到指定核心。

## 调度关系

压缩段仍然是普通 Graph task。建图阶段使用段合并后的读写矩形推导 RAW、WAR 和 WAW 依赖；存在外部依赖的段不会因为压缩而提前执行。依赖满足后，runtime 的 `atomic` 后端通过本地就绪队列、有限窃取和就绪后继的直接 continuation 派发；`current` 指的是这条现有 continuation 调度规则。FIFO 只作为 benchmark 的诊断对照，不是默认策略。

目前整段收齐前驱后才开始执行，整段完成后才通知后继；没有实现逐迭代释放外部依赖。这会引入比细任务图更粗的等待，是段数过少时关键路径增长的原因之一。

段内部由同一个 worker 连续调用官方 ABI，因此它适合访问区域沿行连续移动的循环，也有利于减少任务切换和队列往返。段内部不会把有依赖的调用并行化；只有已经证明相互独立的迭代才被放进同一个可调度段。

## 选择依据和评估口径

离线 `estimate-schedule` 输出任务数、边数、图内存、实例化时间、建图时间和模型 DAG 时间。同一次命令内不同策略共用算子 calibration；跨命令比较不同 `parts` 时，需要先用 `--calibration-out` 保存一次标定，再为各候选传入相同的 `--calibration-in`。模型结果标记为 `model_only`，不计入正式性能排名，也不模拟 NUMA、缓存、真实线程同步、内存带宽或 owner inbox 后端。

统一 calibration 的典型结果显示：完全展开会产生大量任务和边；`parts` 过小会抬高关键路径；`parts` 过大则重新增加建图和通知开销。在已检查的压缩配置中，`current` 通常优于 FIFO，但模型没有证明对所有参数均更快，也没有证明 `workers/2` 最优。该结果只能用于缩小实测候选范围，不能代替 Kunpeng-920 的端到端测量。

正式比较应使用冷数据口径：

```text
warmups = 0
workers = 16, 20, 24
parts = 8, 10, 12, 16
backend = atomic
batch = 1
```

以上 worker 扫描对应用户明确的 16–24 个计算核心要求；在实际获准单 NUMA 内执行。Estimator 默认仍是 `workers=1,2,4,8`、`loop_chunk=1`、`loop_parts=0`，不会自动复现 runtime 的分段策略，因此需要显式传入 `--workers 16 20 24`，以及对应候选的 `--loop-parts`。实际 benchmark 也要显式传入计算线程数和 `--warmups 0`。无预热不等于算子标定保证缓存全冷：当前工具会在计时前初始化缓冲区，模型没有量化冷缓存或段内复用收益。

模型比较可以同时观察以下混合诊断值：

```text
本机 instantiate_seconds + 本机 build_graph_seconds + estimated_dag_seconds
```

它混合了本机准备实测与模拟执行，且不含复制、清零、Metadata 加载、建池和收束等全部阶段，不能当作完整用时或目标机预测值。实际选择依据是目标机完整的 `score_seconds`，辅助观察 `prepare_seconds`、`execute_seconds`、图内存和正确性结果。只看模型算子时间，或者只看图任务数量，都不能证明总用时变快。

`n` 很大且 `b` 很小时，压缩可以显著降低单个内层循环的节点数量；如果外层循环本身仍产生数量级很大的任务，固定 `parts` 只能降低常数，不能替代惰性窗口或流式图构造。
